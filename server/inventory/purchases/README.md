# 入庫一覧

`inventory.zaico.getPurchasesWithCategoryPage` の入力検証・一覧処理と、
`getPurchasesWithCategory` と共通のデータ取得・表示用変換を担当します。
データ取得後の行を受け取り、表示用の形への変換、検索・集計・ページ分割を行います。

| ファイル                                | 責務                                                               |
| --------------------------------------- | ------------------------------------------------------------------ |
| `input.ts`                              | API入力の検証。TypeScriptの入力型もこのスキーマから導出する        |
| `page.ts`                               | 検索、分類・カテゴリ・状態フィルタ、合計・件数、並び順、ページ分割 |
| `localRows.ts`                          | 通常一覧・全件取得で共通の、ローカル発注・明細・在庫情報の表示用変換 |
| `storedExtra.ts`                        | 保存済み配送情報・メモで発注行の空欄を補う優先順位 |
| `localData.ts`                          | 一覧の初期データ取得と、参照在庫の仕入先・出品URL・数量の再取得 |
| `externalRows.ts`                       | 外部在庫由来の発注・在庫・追加情報を表示用の行へ変換 |
| `csvSuppliers.ts`                       | 取引CSVの番号・仕入先名から補完用のマップを作る規則 |
| `items.ts` / `labels.ts`                 | 保存された明細の照合用解釈、管理番号と在庫IDによるラベル照合 |
| `displayStatus.ts`                      | ラベル・入庫履歴・追跡番号から表示状態を決める規則と復旧例外 |
| `inboundClassification.ts`              | 分類設定の取得、手動分類の保護、自動分類結果の保存 |
| `reconcileLabels.ts`                    | 発注明細の数量を超えたラベルの調整と再取得 |
| `shaftBackfill.ts`                      | シャフト在庫に不足する発注の補完と再取得 |
| `../labelViews.ts` / `../managementNo.ts` | 複数の在庫APIが使うラベル表示型・重複排除、在庫備考の管理番号抽出 |
| `../../../shared/purchaseVisibility.ts` | サーバーと画面が共有する日付・発送状態・完了の判定                 |
| `../routers.ts`                         | APIの認証とデータ取得・補完。取得結果を一覧処理へ渡す              |

`page.ts` はDB・HTTP・外部API・Reactに依存しません。取得した行の追加情報は維持し、元の配列や行を書き換えません。
`localRows.ts` と `storedExtra.ts` も接続・更新を行いません。DBの型定義は `import type` だけで参照します。
状態判定・ラベル照合は既存の業務関数を呼出元から渡し、APIファイルへの逆向きの依存を作りません。
出品URL・在庫数量の付加は新しく作った表示明細だけに行います。
分類と最終工程の定義は既存の `shared/inboundPipeline.ts` を使います。
日付・状態・完了条件を変更する場合は画面側に再実装せず、共有側とそのテストを更新します。

## 保持する現行の振る舞い

- 対象日は発注日、旧形式の発注日、旧形式の作成日、作成日の順で探す。判定できる日付がなければ表示対象。
- 通常一覧は入庫済みを除外。完了行は「完了も表示」に応じて含める。
- 検索文字列がある場合、対象日以降の全行から探し直す。分類・カテゴリ・状態の条件を越え、入庫済み・完了済みもAPIには返す。
- 全体合計とカテゴリ合計は検索結果や選択タブだけの合計にはしない。完了表示の指定には従う。
- カテゴリ件数はそのカテゴリを含む発注行数。1行内に同じカテゴリの明細が複数あっても1件。
- 分類タブのバッジは未完了のみ。完了行を含む一覧では未完了を先頭にし、各群内の順序を保つ。

画面側には、返ってきた行への追加の表示制御やタブ件数の補完処理があります。
検索時の画面とAPIの違いも今回の整理では変えていません。DB取得・復旧・自動分類・更新処理の順序と動作も維持しています。

## 通常一覧と全件取得で残す違い

- 全件取得側だけが `createdAt` / `created_at` を返し、有効な入庫履歴も表示ステータスの根拠に使います。
- 通常一覧側は従来どおり、その履歴セットを使いません。ページ分割は通常一覧だけに適用します。
- 外部在庫サービス由来の整形やCSVによる仕入先補完は別の経路として `externalRows.ts` / `csvSuppliers.ts` に分離しています。
- 追加情報は発注ID → 外部ID → 在庫IDの順で1レコードを選び、発注行の空欄だけを補います。
- 壊れた明細JSONは発注行から復元します。有効なJSONが空配列・配列以外だった場合は空明細です。

## データ取得の境界

- 初期取得は発注・在庫・追加情報を並行して読みます。全件取得だけは入庫履歴2,000件を先に読み始め、その読取時間を別に計測します。
- 復旧・数量調整・分類・ラベル取得を終えてから仕入先等を再取得します。順序と各工程の計測は `routers.ts` に残しています。
- 再取得は参照在庫IDで照会し、削除済み在庫も含めます。空IDリストではDBに接続しません。
- DB不在・照会で見つからなかったIDは初期情報を保持します。取得した行はnullや数量0も反映します。
- DBの利用可否と読取時の既存の補助処理は元のDB関数に任せます。新しいキャッシュや接続設定は追加しません。照会エラーは従来どおり呼出元へ返します。

## ラベルと状態の境界

- `items.ts` は照合・状態判定用です。空配列や配列以外のJSONも発注行へフォールバックします。表示用の `localRows.ts` では空明細にするため、両者を同じパーサーに統合しません。
- ラベルIDの重複比較はtrim・大文字化し、表示の綴りは保持します。在庫IDのある既存ラベルをIDなしの後続ラベルで置き換えないという例外も維持します。
- 管理番号の一致は大文字・小文字を区別します。管理番号が空のラベルも従来どおり対象になります。在庫ID一致の発注ラベルがあれば優先し、在庫側のラベルも合わせて重複を除きます。
- 保存状態がpurchasedでない場合、追跡番号・shippedを履歴や受領ラベルより優先します。必要な受領数の計算、復旧した特定管理番号の例外も変更していません。
- 一覧表示・入庫履歴の復旧・ラベル照合・削除対象の判定などの既存呼出元がこの共通定義を参照します。呼出順序とAPIの入出力は `routers.ts` に残します。
- `managementNo.ts` はカンマだけで区切り、番号内の空白を保持します。`shared/ebayInventory.ts` の種別判定用抽出は空白でも区切るため、同じ処理として扱いません。

## 一覧読取中に書き戻す処理

- 自動分類の業務規則は `shared/inboundPipeline.ts` が正本です。`inboundClassification.ts` は設定・在庫・発行済みインボイスを集め、手動分類を保護し、保存値との差分だけを書き戻します。保存に失敗しても表示には計算値を使う既存挙動を保持します。
- `reconcileLabels.ts` は数量超過だけを調整します。ラベル不足は補充しません。削除するラベルの選択は既存のDB関数に任せ、更新失敗は呼出元へ返します。
- `shaftBackfill.ts` は削除済みでないシャフト在庫について、発注行または明細etcに管理番号がなければ発注を補完します。手動で行うシャフト分離とは別です。保存が一件失敗しても次を処理し、一件以上成功した場合だけ再取得します。
- 孤立ラベルからの発注復旧、許可対象の復旧後整理はまだ `routers.ts` に残っています。対象を限定したテストを先に追加してから別の単位で整理します。

## 外部在庫由来の経路について

現在の `isZaicoEnabled()` はfalseを返し、Zaico API関数自体も無効化されています。
この整理ではその状態を維持し、残っている表示用変換だけを分離しました。
外部APIの型とDBの追加情報型は既存定義を `import type` で参照します。

- 通常一覧だけがラベル取得後に変換し、現在庫数・表示用ラベルを付加します。CSVは読みません。
- 全件取得だけがCSVを読みます。在庫情報のマップ作成→CSV取得→表示用変換の順序は従来どおりです。
- 仕入先は明細順で最初に名前かURLがある追加情報を採用し、空文字をnullと同一視しません。
- カテゴリは配列の先頭→単一カテゴリ→未分類の順。備考はカンマを含む完全形式を優先する既存ルールを共通化しています。
- 同じIDが複数ある場合は最後の情報を採用します。元の発注・明細の追加項目を保持し、入力データは変更しません。
- CSVは先頭3行を除外し、C列の数字の番号ごとに最初の非空のN列を採用します。行パーサーは既存の `parseCSVLine` を渡し、重複実装を作りません。
- CSV失敗時は従来どおりエラーを記録し、取得済みの補完情報で一覧を返します。

固定値によるAPIテストではこの経路をテスト内だけで選択します。外部サービスとの実接続や認証の検証ではありません。
