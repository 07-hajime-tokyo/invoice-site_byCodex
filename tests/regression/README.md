# 入庫管理の回帰テスト

UI・機能を保ったまま責務分割とSSOT整理を行うための、整理前の比較基準です。
基準のアプリコードはコミット `112886f`。本体の挙動は変更していません。

## 実行環境

Node.jsと依存パッケージ、ローカルMySQL 8.4、専用の空DBが必要です。
このPCではDockerの `invoice-remake-mysql` を使用します。

| 用途               | 接続先          | DB                  |
| ------------------ | --------------- | ------------------- |
| 通常のローカル開発 | 127.0.0.1:33067 | invoice_remake_dev  |
| このテスト専用     | 127.0.0.1:33067 | invoice_remake_test |

テスト用ユーザー `invoice_test` にはテストDBだけの権限を与えます。
`.local/test.env` にその接続URLを設定します。実際のパスワードはコミットしません。
このPCでは `.local/` を `.git/info/exclude` で除外済みです。別PCでも最初に除外してください。

```dotenv
DATABASE_URL=mysql://invoice_test:<URLエンコードしたローカル専用パスワード>@127.0.0.1:33067/invoice_remake_test
```

## コマンド

リポジトリのルートで実行します。最初の1回だけテーブルを作成します。

```sh
node scripts/test-local-regression.mjs schema
```

整理前と整理後に同じコマンドで確認します。

```sh
pnpm test:regression
pnpm check:regression
```

**テストとseedは、毎回テストDB内の全テーブルのデータを消して架空データに戻します。**
実データや手元作業用データをこのDBに入れないでください。画面操作と同時に実行しないでください。
テスト終了後に画面確認用の初期データへ戻すには次を実行します。

```sh
node scripts/test-local-regression.mjs seed
```

このPCの画面確認は `.local/visual-start.sh` で起動し、
`http://localhost:3001/inventory/purchases` を開きます。
通常開発の3000番とはDBが異なります。画面の確認手順は `browser-checklist.md` を参照してください。
`.local/` の起動設定・認証情報はこのPC専用で、リポジトリには含めていません。

## 責務の分け方

| ファイル                          | 責務                                               |
| --------------------------------- | -------------------------------------------------- |
| scripts/test-local-regression.mjs | 専用設定読込・環境を絞った子プロセス起動           |
| support/test-target.mjs           | 使用できるDBの接続先定義・検証                     |
| support/network-guard.mjs         | Nodeの通常のTCP接続・fetchをループバック宛てに制限 |
| support/database.ts               | 専用DBを確認して初期化・架空データ投入             |
| purchase-fixtures.ts              | APIテストと画面確認で共有する架空データの定義      |
| support/api.ts                    | 実際のExpress/tRPCをローカルHTTPで起動・終了       |
| purchases.test.ts                 | 通常一覧・全件取得・編集に対する21件の期待結果      |
| test-target.test.ts               | 接続先の相違を拒否する1件の安全性テスト            |
| seed.ts                           | 画面確認用データの復元入口                         |
| vitest.config.ts / tsconfig.json  | 実行対象・型チェック対象の設定                     |

パスワードや外部APIキーを親プロセスからテストへ引き継ぎません。
接続URLと接続後のDB名を確認し、テストDB以外は初期化しません。
ネットワークガードはNode用の補助策でありOS全体のファイアウォールではありません。
既存の `pnpm test` にはこのDB依存テストを混ぜていません。

## 自動テストの対象

実際のHTTP → API → MySQL → 再取得を通します。業務ロジックやDBをモックしません。

- 一覧件数・分類別件数・完了済み/入庫済み/対象日前データの扱い
- 小数単価×数量、カテゴリ別・全体の金額
- 分類・カテゴリ・発送状態による絞り込み
- 完了表示、商品名/管理番号/追跡番号の検索、該当なし
- ページ分割、範囲外ページ補正、不正入力
- 追跡番号の保存・解除と発送状態、メモの保持
- 商品編集の発注行・在庫行・JSON明細への保存と再取得
- 全件取得の作成日時、有効/取消済み入庫履歴による状態の違い
- 追加情報の空欄補完、壊れたJSONの復元、空配列/配列以外のJSONの扱い
- 在庫変更の再取得への反映、削除済み在庫の仕入先補完、空DB、各工程の計測順序

現在のAPIでは検索時に分類等の条件を越えて入庫済みの行も返します。
これは今回修正せず現行動作として固定しています。画面にはさらに表示条件があるため、
APIの結果だけで画面全体を保証しません。

## この段階で保証しないこと

画面全体の自動画像比較、新規発注・入庫確定・出庫・削除、インボイス等の他画面、
本番認証/権限、外部API・Google連携・AI、実データの例外・大量データ性能は未検証です。
別の範囲を整理する前に、その範囲の整理前テストを追加します。
期待値は「望ましい新仕様」ではなく「現行の結果」です。既存の問題の修正は別の変更に分けます。
